# AGENTS.md

## Overview

- This repo holds the openipdata.org data workers, workflows, builders, and the website service in `site/`.
- Workflows are being moved here from another repo step by step. This repo must stay self-contained: no imports, submodules, URLs, or file references to other repos. Reproduce anything needed here.

## Layout

- `site/`: standalone Go module (`package main`, binary `openipdata-site`): the openipdata.org website, one static binary behind nginx behind Cloudflare. It may share the worker VM (decided 2026-11-14), but stays fully separate: its own user, `/opt/openipdata-site`, `/var/lib/openipdata-site`, and its data only from the GitHub releases, never the worker's files under `/var/lib/openipdata`. It must not import `hatchet`, `mmdbbuilder` or `iplistener`; its only third-party dependencies are the MMDB reader and the SQLite driver `modernc.org/sqlite` (pure Go, the same version as the worker's, so the binary stays a static `CGO_ENABLED=0` build; a new dependency needs the owner's OK). Templates, CSS and the two font files are embedded (`go:embed`).
- `infra/`: VM provisioning (`init-hatchet-runner-vm.sh`), systemd unit, env template. No Go code. `infra/site/` holds the website VM setup (init script, updater, MMDB puller, Cloudflare range script, nginx files, systemd units; no Go code).
- `hatchet/`: Go module for `openipdata-worker`, the Hatchet worker. `main.go` registers workflows; each workflow lives in its own folder (`hatchet/asn/` for `build-asn-data`, `hatchet/pdb/` for `sync-peeringdb`, `hatchet/domains/` for `update-asn-domains`, `hatchet/geofeeds/` for `sync-geofeeds`, `hatchet/bgp/` for `sync-bgp`, `hatchet/geo/` for `build-geo-data`, `hatchet/rdns/` for `resolve-ips`, `hatchet/rdnsrules/` for `learn-rdns-rules` with its tasks `learn` and `propose-codes`, `hatchet/mlab/` for `import-mlab` and `import-mlab-sites`, `hatchet/arin/` for `sync-arin-whois`). `hatchet/schema/` creates and upgrades the shared Postgres tables; `hatchet/publish/` uploads artifacts to R2 and GitHub releases (a file that is already there byte-for-byte is not sent again) and downloads the R2 layer files; `hatchet/rirstats/` parses RIR delegated-extended stats and splits address ranges into prefixes; `hatchet/download/` downloads a file unless the local copy is current (the caller passes the HTTP client); `hatchet/outputs/` prunes old output directories and has the small helpers `asn` and `geo` share (last log lines, file size); `hatchet/ipdata/` has what several workflows need about IP space and `public.asn` (public-address check, country-code check, announced prefixes of `public.asn.json`, the `seen_at` filter). Workflows share this code, never each other's downloaded files.
- `mmdbbuilder/`: Go module for `mmdbbuilder`, a standalone CLI (`package main`) with one subcommand per database (`asn`, `geo`), plus `eval` (scores a geo MMDB), `lookup` (reads one: a report, or with `-in`/`-out` the city of each IP of a file; a guess city is left out; `-with-source` adds a fourth column, the record's `city_source`, and `-countries` with it also writes IPs that have a country but no city, with an empty city; without the flags the output is byte-identical to before) and `gaps` (the IPv4 /24s of a geo MMDB with a country and no city (a city whose `city_source` is one of the six guesses (`80-asn-main`, `82-asn-likely`, `84-asn-near`, `85-holder-city`, `86-country-main`, `88-asn-far`), `25-bgp`, `35-speedtest-site`, `36-mlab`, `37-whois-arin`, `37-whois-text` or `39-github-geofeeds` counts as none, so `sample-names` keeps sampling customer names there (right 82% of the time against 68% for the whois text); the list is `noSampleSources` next to `isGuessSource` and `guessSources`), as runs `<first /24> <count> <country>`; a /24 split between countries, or with a city in any part, is left out). `geo -asn-main <asn-prefixes.csv.gz>` adds the guessed ASN main city fill after all layers, `geo -fallback` four more guesses after it, and `geo -holders <holder-cities.csv.gz>` one for address space no network announces (see the ASN main city fill, the fallback guesses and the holder city guess rules).
- `tools/llm-codes-test/`: scratch Python test (standard library only), not run by the worker: compares LLMs (through OpenRouter, key only in `OPENROUTER_TEST_API_KEY`) on proposing city codes for router-name domains. It sends router hop names only, never visitor names; its exports and answers are git-ignored.
- `tools/mapdata/`: standalone Go module (`package main`, standard library only, run by hand, not by the worker or the site build): turns the Natural Earth 1:50m country outlines (public domain GeoJSON, not in Git) into `site/static/world.bin`, the file the website draws its map from. Source, licence, input hash and the command are in `tools/mapdata/README.md`.
- `iplistener/`: standalone Go module (`package main`) plus install script, unit and env template; it runs on the web servers that serve visitors, not on the worker VM. It tails the nginx access log and upserts visitor IPs into `public.visitor_ips`. It must not import `hatchet` or `mmdbbuilder`; it reproduces small helpers (e.g. hiding the DSN in pgx errors).
- `beacon/`: standalone Go module (`package main`, binary `openipdata-beacon`, dependencies: `golang-dnstap`, `miekg/dns`, `go-redis`, `protobuf`) for the web VM. Knot DNS serves the zone `r.openipdata.org` and sends each query through dnstap to a unix socket; the daemon stores the address of the resolver that asked for `<32 hex>.r.openipdata.org` in Redis (contract in the "Server" bullet). It must not import `hatchet`, `mmdbbuilder`, `site` or `iplistener`.
- No `go.mod` or Go code at the repo root. Each module builds on its own.
- `hatchet` must not import `mmdbbuilder`; it runs the `mmdbbuilder` binary (and, for `resolve-ips`, `scamper`) found next to its own executable.

## Website decisions (2026-11-14)

- Stack: Go only. `net/http` plus `html/template` parsed once at start; no Node, npm, Astro, client framework, CSS tool or other build step. Do not change the stack without discussing it.
- Pages are server-rendered and as light as possible: all CSS inlined in the page, no images (one exception: the home-screen icon PNG, below), no map SDK, no JavaScript except the inline theme switch and the one small inline script that fills in the second address (below); the page works without both. Nothing may block rendering: any script sits at the end of the body and only fills in extras after the page is shown, extra requests are asynchronous with a timeout, and the page is complete without them. The only other requests are the two self-hosted Geist Latin `woff2` files (`/fonts/`, one-year immutable cache). No third-party request of any kind.
- Design: "Console" (dark-first panels with hairline borders, Geist for labels, Geist Mono for data, one orange accent, dark and light themes; header = logo, GitHub icon, theme icon). Very little text: no taglines, hints or filler. No flag emoji (Windows does not render them).
- Implemented now: the home page with the lookup bar (a plain `GET /` form, field `q`), the "Your connection" panel (title "Lookup" for `/?<ip>`) and the Accuracy panel. The connection panel has two halves, the data rows FIRST (left on desktop, on top on a phone) and the place block with the map SECOND (right, below); the place is the city and country, country alone with no second line, or "Location unknown". Rows of the visitor's own page, in this order: IPv4, IPv6, DNS resolver, Network (no Prefix row, no AS number). Rows of a lookup page: the looked-up address (IPv4 or IPv6), Network, Prefix (the announced prefix, linked to its prefix page). The Network row (2026-11-15) is `BT-UK-AS · ISP · bt.net`: the network's short name (handle, from the loaded ASN data) as a link to `/as<n>`, its category (`$.metadata.category` of the row's json; `isp` shown as `ISP`, others with a capital first letter and spaces for underscores), its domain (`asn_domain`), joined by ` · `, an unknown part left out; with none known, or without ASN data, the organisation or name text of the ip2asn MMDB as plain text (else `AS<n>`, else a dash). The handle comes from the in-memory record; category and domain are read per page view with one parameterised query by number under the read lock of `asnFile` (`site/netinfo.go`), not kept in memory. The IPv4 and IPv6 values have a small copy button (inline SVG icon, `aria-label="Copy"`, rendered `hidden` and shown by `static/panel.js`; the other family's button is shown by `fill.js` when its address arrives); a click copies the address and shows a check mark for 1.5 s. `/?q=<ip>` and any non-canonical spelling of an address (upper case, percent-encoding, spaces, IPv4-mapped) redirect to the canonical `/?<ip>`; `/?q=<ip>` and any non-canonical spelling of an address (upper case, percent-encoding, spaces, IPv4-mapped) redirect to the canonical `/?<ip>`; what else the box takes is in "Lookup box" below, anything it cannot read gives 400 "Not an IP address, AS number or name"; a non-public address (`isPublic` in `site/lookup.go`) is shown with "Not a public address" and not looked up. Both MMDBs stay open for lookups and are swapped on change (`sync.RWMutex`, never closed under a lookup); a missing file only gives unknowns; addresses are never logged. The Accuracy numbers come from the stamp in the ip2geo MMDB's metadata (`description.openipdata`, written by `build-geo-data` `evaluate`): "right country" = `atlas_country_pct`, "right city" = `atlas_city_pct`, "of addresses have a city" = `city_pct`, the device count = `atlas_probes`, "updated" = `built_at`. The website reads no Postgres table and no status file.
- Unknown stays unknown: a missing score is shown as a dash, a missing city is not shown (the country stands alone, no second line), a missing location is "Location unknown"; never a sample, default or "estimated" value. The loopback connection is not a public visitor address.
- Cache: `/` shows the visitor's data, so it is `private, no-store` with no `ETag`; a lookup page (`/?<ip>`) shows none, so it is `public, max-age=300` (never put the visitor's own address on it); a bad query is `no-store`; an empty `q` (the empty lookup box) redirects to `/`, and the redirects to the canonical URL use the same cache header as a lookup page; a lookup page has the address in its `<title>`. Each MMDB is opened and watched in one place (`mmdbFile`); the scores are read from the metadata of the open ip2geo reader. The client IP is the header named by `REAL_IP_HEADER` (default `X-Real-IP`, also set in the unit, so a new binary under an older unit still works; set to empty = no header trusted, the TCP peer is the visitor), trusted only when the connection comes from loopback (nginx, which always overwrites that header with `$remote_addr`, the visitor after the Cloudflare real-IP step); a missing or invalid value means unknown, never the proxy's address. A non-loopback peer is the visitor itself, except a private or link-local peer while a header is set (a proxy moved off loopback): unknown. Site settings: `LISTEN`, `GEO_MMDB`, `ASN_MMDB` (default `/var/lib/openipdata-site/data/ip2asn-openipdata.mmdb`), `ASN_SQLITE` (default `/var/lib/openipdata-site/data/asn-openipdata.sqlite3`), `REAL_IP_HEADER`, set in the unit; `SHARE` (`on` default, `off`) and `SITE_ORIGIN` (default `https://openipdata.org`) are read by the binary and not set in the unit. `TEST_IP` (empty by default; local work only, never set on a server): the visitor address of a request that comes straight from loopback WITHOUT the real-IP header, so a local run shows a full visitor page; behind nginx, which always sets the header, it changes nothing (`testAddr` in `site/lookup.go`; the start line names the header, never the address). Every local run or preview of the site sets it.
- Server (implemented, files in `infra/site/`; `site/README.md` has the commands): one Ubuntu 24.04 VM behind Cloudflare, installed by `infra/site/init-openipdata-site.sh` (idempotent, never overwrites the env file, never obtains the certificate). User `openipdata-site`; `/opt/openipdata-site/{bin,releases,slot-8080,slot-8081}`, the MMDBs and the ASN SQLite file in `/var/lib/openipdata-site/data`, updater state in `/var/lib/openipdata-site/state` (root), env `/etc/openipdata-site/openipdata-site.env` (`GITHUB_REPO`, `HC_PING_SITE`, `HC_PING_MMDB`, `NTFY_URL` (an ntfy.sh topic URL: the updater sends one push when a new build goes live, nothing else; empty = none; a failed push only logs; never logged); the site service reads no env file). Units: template `openipdata-site@.service` (hardened, instance name = port, `LISTEN=127.0.0.1:%i`, two instances `@8080` and `@8081` take turns), and oneshot plus timer for `openipdata-site-update` (root, 2 min), `openipdata-mmdb-pull` (as `openipdata-site`, 10 min) and `openipdata-cf-ips` (root, weekly). Updater (blue/green): reads the `.sha256` asset of the release `site` (missing, empty, invalid, download failed or binary hash different = upload in progress, try later, no ping), skips the installed hash, never retries the hash in `bad.sha256` (pings `/fail` each run). The symlink `/etc/nginx/conf.d/openipdata-site-live.conf` -> `/etc/nginx/openipdata-site/upstream-<port>.conf` is the ONLY record of the live port (no state file; missing link = fail, run the init script; the init script creates it once, pointing at 8080, and never changes it). Every run first starts the live instance if it is inactive. A new build goes to `releases/<sha>.tmp`, `-version` runs unprivileged under `timeout 10` (a binary that ignores the flag and starts a server must not block the updater), `slot-<idle>` is pointed at it, `openipdata-site@<idle>` restarted, and only `/healthz` = `ok <version>` within 20 s passes. A bad build never touches the live side: the idle instance is stopped, the slot restored, the hash goes to `bad.sha256`, `/fail` is pinged. A good build: the link is switched atomically, `nginx -t`, graceful `systemctl reload nginx` (skipped when nginx is not active); an nginx failure restores the link, stops the idle instance and pings `/fail` but does NOT mark the build bad. Only the live instance is enabled (new one enabled, old one disabled); after `DRAIN` s (10) the old instance is stopped; keeps the releases both slots point to plus the 3 newest. The init script migrates the old single `openipdata-site.service` once (starts `@8081` on the same release, switches the link, then removes the old unit and `current`; on failure the old service keeps running). Data puller (`openipdata-mmdb-pull`; MMDBs and the SQLite file): one conditional API call to the release `latest` (ETag saved in `.release.etag` with the body in `.release.json`, written only after a fully successful run; `If-None-Match`, 304 reuses the saved JSON and every file is still checked against its key), files `ip2geo-openipdata.mmdb`, `ip2asn-openipdata.mmdb` and `asn-openipdata.sqlite3` (the worker must publish the last one to the release `latest` first; until it does, with no local copy each run logs `not published yet`, which is not a failure; once a local copy exists, an absent asset is a failure), change key = asset `digest` or `updated_at|size` saved as `<name>.key`, size and digest checked, `.tmp` plus rename, an MMDB asset that is missing, or any failure, keeps the old file and pings `/fail`. nginx: `default-deny.conf` (catch-all 444 and `ssl_reject_handshake`, no certificate needed) is always enabled, so the origin is closed before the certificate exists; only Cloudflare ranges reach the site (a generated `geo` sets `$from_cloudflare`, others get 444; plain allow/deny cannot be used because it tests the address after realip), real IP from `CF-Connecting-IP`, ranges refreshed weekly and refused when empty or invalid, `nginx -t` before reload with the old file restored on failure, `/healthz` is a 404 through nginx, access log `/var/log/nginx/openipdata.org.access.log`. Certificate: certbot with the Cloudflare DNS challenge at `/etc/letsencrypt/live/openipdata.org/`, covering `openipdata.org` and `*.openipdata.org` (www is not served; any other host gets the default-deny answer), obtained by hand (the script prints the command; without the certificate the nginx site stays disabled), renewal hook reloads nginx. ufw: the real sshd ports (`sshd -T`, fallback OpenSSH profile or 22 with a warning), 80, 443. Pings: a normal run pings the URL, a failure pings `<url>/fail`, empty does nothing, URLs never logged.
- DNS resolver beacon (implemented, backend; files in `beacon/`, `infra/site/knot/`, `infra/site/systemd/openipdata-beacon.service`, `infra/site/nginx/r.openipdata.org.conf`; the init script sets it up when it knows the VM's public IPv4: the address of `v4.openipdata.org` (and of `v6.openipdata.org` for IPv6) when it is a global address of this machine, or `PUBLIC_IPV4`/`PUBLIC_IPV6` in the env file, which override; otherwise one line says it is skipped). A browser looks up the one-time name `<32 hex>.r.openipdata.org`; Knot DNS (listens only on the VM's public addresses and 127.0.0.1, port 53, UDP and TCP; zone from a generated file with a wildcard A/AAAA at the VM, TTL 0, serial = Unix time of the run that changed the content; `mod-rrl` 300 responses/s per prefix, slip 2; no zone transfer; no queries logged; ufw allows 53) sends each query by `mod-dnstap` to `/run/openipdata-beacon/dnstap.sock`; `openipdata-beacon` (own user, group `knot` on the runtime directory 0750, socket 0660, starts before Knot, binary `/opt/openipdata-site/bin/openipdata-beacon`, installed by `openipdata-site-update` from the asset `openipdata-beacon-linux-amd64` of the release `site`, a separate part that never stops the site update: bad build = old binary back, `/fail` ping) writes to Redis. Redis: `127.0.0.1:6379` only, no password, RDB snapshots on (`save 900 1`, `save 300 100`, `appendonly no`; since 2026-11-15, because the website keeps shared reports in it, see "Share"), `maxmemory 256mb` with `volatile-ttl` (keys that expire soonest go first: beacon keys, one hour or less, before reports, 30 days); the same Redis holds the `report:<id>` keys of the website. Contract with the site: key `beacon:<token>` (token = 32 lower-case hex, first label, case folded; any other name ignored), hash with ONE field `resolver_ip` (canonical address, IPv4 unmapped), `HSETNX` (first query wins) then `EXPIRE <BEACON_TTL>` only when the key was created (the binary default is 120 s; the unit sets `BEACON_TTL=3600` since a visitor may press Share minutes after the page loaded; the init script restarts `openipdata-beacon` when its installed unit file differs from the one in the repo); nothing else is stored (no EDNS client subnet, no query type) and no address, token or name is ever logged (only start settings and error counts). HTTPS on the one-time name: certificate `*.r.openipdata.org` by certbot with the DNS challenge answered by Knot (`python3-certbot-dns-rfc2136`; a TSIG key made once by the init script into `/etc/knot/openipdata-acme-key.conf` and `/etc/letsencrypt/openipdata-r-rfc2136.ini`, root only, never shown; the Knot ACL lets only that key, from 127.0.0.1, update TXT at `_acme-challenge` of the zone; `zonefile-sync: -1` so Knot never writes the generated zone file); like the main certificate the script never obtains it and prints the command. `nginx/r.openipdata.org.conf` (enabled only with that certificate) matches only `<32 hex>.r.openipdata.org`, refuses Cloudflare peers (403), serves only `GET`/`HEAD` of `/` as `/resolver?t=<token>` on the live site with `X-Real-IP` = TCP peer, 10 r/s per address, own log `r.openipdata.org.access.log` with time, visitor address (TCP peer), status, method, path, request time and User-Agent but NEVER the host (the token; address plus token would tie a visitor to their resolver; owner, 2026-11-18), adds no CORS header. The site's DNS row is OFF by default (`BEACON_ZONE` empty in the binary); the init script writes the drop-in `/etc/systemd/system/openipdata-site@.service.d/beacon.conf` (`BEACON_ZONE=r.openipdata.org`, `REDIS_ADDR=127.0.0.1:6379`) only while that nginx site is enabled and removes it otherwise, restarting the live site instance only when the drop-in changed. The site unit's hardening allows the loopback TCP connection to Redis (no `IPAddressDeny`, no `PrivateNetwork`).
- Both addresses (decided 2026-11-15): a browser connects over one family, so `GET /ip` (and HEAD; `text/plain`, canonical address plus newline, `no-store`, `Access-Control-Allow-Origin: *`, 503 `unknown` when unknown, same `clientAddr` rules, never logged) answers the visitor's own address, and the page asks the other family on a name that exists in one family only: `v4.openipdata.org` (A record only) and `v6.openipdata.org` (AAAA record only), DNS-only names that point straight at the web VM, NOT through Cloudflare (`openipdata.org` stays behind it); they expose the VM's address by design. The wildcard certificate covers them. Their nginx file `infra/site/nginx/v46.openipdata.org.conf` (installed and enabled like the main file) accepts direct visitors only: a request whose TCP peer is a Cloudflare address (`$from_cloudflare` = 1) gets 403 on every path and both ports, because a proxied request would show Cloudflare's address as the visitor's second address (the address is `$realip_remote_addr`, the TCP peer, so a client's `CF-Connecting-IP` never counts), serves only `location = /` (GET and HEAD, proxied to `/ip` with `X-Real-IP` always set), answers 404 for every other path without reaching the site, limits each address (`limit_req`, 5 r/s), has a 1k body limit and its own access log without addresses. Settings in the unit: `V4_URL` (default `https://v4.openipdata.org/`) and `V6_URL` (default `https://v6.openipdata.org/`), each an absolute `https://` URL (`http://` only for `127.0.0.1`/`localhost`) or empty; empty for the missing family = no second row and no script. The visitor's own page (public address only) shows an IPv4 row and an IPv6 row; the server fills its own family, the other shows a dash that the script (`site/static/fill.js`, last thing in the body, starts after the HTML is parsed, 4 s abort, strict check of the answer, `textContent` only) fills in. That script, `resolver.js` (the DNS row, below) and `panel.js` (copy and share buttons, see "Share") are the ONLY JavaScript besides the theme scripts. The page requests plain `<url>`; only after the visitor pressed Share does `panel.js` request `<url>?r=<report id>` once more, so `/ip` can add the address to the report (nginx passes the query string: `proxy_pass` with a URI keeps the arguments). The five scripts (`site/static/head.js`, `theme.js`, `fill.js`, `resolver.js`, `panel.js`) are plain files embedded with `go:embed` and put inline into the page; the CSP hashes come from the same text at start (`scriptText` in `site/page.go`), and an empty file stops the start. Its hash is in `script-src` and `connect-src` lists exactly the origins of the two URLs, only on a page that has the row (every other page keeps the CSP without both). No resource hints for the two hosts. Command-line clients and common Go, Python and JS HTTP libraries (list in `isCLI`, `site/ipapi.go`, by User-Agent only) get the `/json` answer instead of the plain address on `/ip` when the request Host is the name of `V4_URL` or `V6_URL` (`openipdata.org/ip` stays plain for everyone); `/ip` always has `Vary: User-Agent`.
- DNS row (implemented 2026-11-15, site part; code `site/resolver.go`, `site/redis.go`, `site/static/resolver.js`; backend in the "DNS resolver beacon" bullet): the visitor's own page (public address only) gets a row "DNS resolver" (a dash, hidden behind three CSS-only waiting dots for about 80 s at most) that `resolver.js` (last in the body, after `fill.js`, own CSP hash, `connect-src https://*.<zone>` only on that page) fills like the owner's other site does: the resolver's IP ADDRESS as a link to its lookup page `/?<ip>`, then the SHORT network name (the `name` of the ip2asn record, e.g. `GOOGLE`; the organisation only when there is no name) in a `<small>` (muted, 13px, 8px from the address), linked INSIDE the `<small>` to the organisation page when known (the same form on the report page); no AS number (2026-11-16). The script makes its own 32-hex token with `crypto.getRandomValues` (the server makes none; the report id never appears in a DNS name) and leaves it in `data-t` of the `#dns` element, where `panel.js` reads it when Share is pressed; it fetches `https://<token>.r.openipdata.org/` (first a request to `/t` of that name that only causes the DNS lookup (nginx answers 204, the site is not asked), then, 2.2 s later (Knot reports lookups in batches up to two seconds late), `/` of that name; after a 404 again every 2 s, 8 tries on that name (16 s); then, or at once after any other failure, ONE second name with a new token (a lost lookup or a wrong answer the browser keeps for the first name cannot be repaired on it), 30 tries (a minute), 3 s abort each; a failure on the second name leaves the dash; `data-t` always holds the newest token; the site never holds a request open to wait); nginx proxies that to the site's `GET /resolver?t=<token>`, which reads `HGET beacon:<token> resolver_ip` from Redis on loopback with a tiny standard-library client (300 ms deadline, no dependency) and answers JSON `{"ip","name","org"}` (`org` = `/asn-<slug>` or, without a slug, `/as<n>`; unknown fields left out; 404 not there yet, 503 Redis down, 400 bad token; `no-store`, `Access-Control-Allow-Origin: *`). `/resolver` only reads; it never touches a shared report (the report reads `beacon:<token>` itself, see "Share"). The resolver address is sent to the page (it is the resolver's, not the visitor's); neither it nor the token is ever logged. Settings: `BEACON_ZONE` (EMPTY by default = no row, no script, `/resolver` 404; the init script sets it in a drop-in only while the nginx site of `r.openipdata.org` is enabled, so the row never appears before the chain works) and `REDIS_ADDR` (loopback only, default `127.0.0.1:6379`).
- ASN pages (implemented 2026-11-15; code in `site/asn.go` and `site/asnpages.go`, templates `layout.html` (shared header and lookup bar) and `asn.html`, styles `static/asn.css`, added to the page only on ASN pages so the home page does not grow; no new script, the same two inline theme scripts). Data: the SQLite file `asn-openipdata.sqlite3` (tables as written by `hatchet/asn/export.go`: `asn`, `asn_domain`), opened read-only and immutable (`file:...?mode=ro&immutable=1`), loaded again when its size or mtime changes (checked every 30 s with the MMDBs; `asnFile`, same care as `mmdbFile`: read and built outside the lock, swapped under the write lock, the old handle closed only after the swap; requests render into a buffer while they hold the read lock, never write to the client under it; one log line per distinct error with the path; a failed reload or a vanished file keeps what is loaded). - Local resolver: `unbound` on `127.0.0.1:5335` (loopback only, no query log, no DNSSEC validation), config `/etc/unbound/unbound.conf.d/openipdata.conf` written by the init script on every run (`unbound-checkconf` first; on failure the file is removed and the worker keeps the system DNS). Only the worker's PTR lookups use it: the script writes the unit drop-in `/etc/systemd/system/openipdata-worker.service.d/ptr-resolver.conf` (`PTR_RESOLVER=127.0.0.1:5335`) only after a passing `dig` smoke test and removes it otherwise; a `PTR_RESOLVER` line in the env file overrides it (empty = off). The system DNS (systemd-resolved, `/etc/resolv.conf`) stays as it is; the packaged `unbound-resolvconf.service` is disabled.
- Env file: `/etc/openipdata/worker.env` (root:openipdata, 0640); template in `infra/`.
- State: `/var/lib/openipdata` (openipdata, 0750); the only writable path for the service.
- Build cache: `/var/cache/openipdata-build` (root, 0700): pinned Go toolchain plus module/build caches; safe to delete.
- `infra/init-hatchet-runner-vm.sh` is idempotent and never overwrites an existing env file. It is for the first setup (and scamper, unbound, units); worker code changes no longer need it. It holds the flock `/run/openipdata-worker-deploy.lock` for its whole run.
- Worker auto-deploy (2026-11-15; `.github/workflows/worker.yml`, `infra/openipdata-worker-update` with its `.service`, `.timer` and `.env.example`; same patterns as the website, see "Server" and "Build" above). A push to `master` that changes `hatchet/**`, `mmdbbuilder/**` or the workflow file (or a manual run) runs gofmt, `go vet` and `go test -race` in both modules, builds static linux/amd64 `openipdata-worker` and `mmdbbuilder` (`-X main.version=<commit sha>`) and, only on `master`, replaces the assets of the rolling release with the tag `worker` (never latest, tag never moved): the two binaries first, then ONE manifest `worker.sha256` last (two `sha256sum` lines for `openipdata-worker-linux-amd64` and `mmdbbuilder-linux-amd64`, then the line `version <version>`). Both binaries answer `version` (prints the version, needs no environment). The timer runs the updater as root every 2 minutes under `flock -n` on the deploy lock (locked = exit 0 quietly). It reads the manifest (missing or not exactly those 3 lines = upload in progress, no ping), compares the hashes with the files actually installed in `/opt/openipdata/bin` (no installed-state file), skips a manifest remembered in `/var/lib/openipdata-update/bad.sha256` (pings `/fail` each run), downloads and checks both assets (mismatch = try later), runs each `version` unprivileged under `timeout 10` (must print the manifest's version, else bad), waits for an idle worker, installs (`<name>.prev` copies, root 0755, temp name plus `mv`), restarts the service only when it is enabled and the env file has a `HATCHET_CLIENT_TOKEN`, watches it 30 s (active, `NRestarts` unchanged); a crash loop puts the `.prev` binaries back, writes `bad.sha256`, pings `/fail`, exit 1. Idle wait: the worker keeps the file `/var/lib/openipdata/worker-busy` (`busyMarker` in `hatchet/busy.go`, one `worker.Use` middleware: exists exactly while a task runs, removed at `serve` start and on shutdown, a write failure only logs); the updater waits while the service is active and the file exists (checked before the download and again before the install), for at most 45 minutes counted from `waiting-since` (`<epoch> <manifest sha>` in the state dir, reset when the manifest changes), then installs anyway (Hatchet retries interrupted tasks). Settings in the optional `/etc/openipdata/worker-update.env` (`GITHUB_REPO`, `HC_PING_WORKER_UPDATE`, `NTFY_URL`, never logged; `NTFY_URL` = an ntfy.sh topic URL, one push after each install, empty = none, a failed push only logs). Rollback: push a revert (a new build is installed the same way), or pause the timer (`systemctl disable --now openipdata-worker-update.timer`) and rerun the init script from an older checkout. Stays manual: first setup, scamper, unbound, the unit and env file (init script), secrets. The updater never touches those.

## Rules

- Keep it simple: read env vars directly in `main.go`; no config packages or frameworks.
- Use the standard library where possible (e.g. `encoding/json`).
- Postgres is the source of truth; the VM only keeps caches and the last few builds.
- Output files (MMDB, SQLite) are rebuilt from scratch each run and written via a `.tmp` file plus rename.
- One writer per table; every other workflow only reads it:
  `public.asn` ← `build-asn-data`, `public.asn_geo_pdb` ← `sync-peeringdb`, `public.asn_domain` ← `update-asn-domains`,
  `public.geo_ix_pdb` ← `sync-peeringdb`, `public.geo_eval` ← `build-geo-data`, `public.geofeed_urls` ← `sync-geofeeds`,
  `public.visitor_ips` ← external websites insert through `iplistener` (insert, or update of `last_seen_at` only); `resolve-ips` is its only deleter (exception to one writer: it never inserts or updates),
  `public.network_traces`, `public.traced_networks`, `public.ip_ptr_names`, `public.customer_name_networks` and `public.rdns_geo_layer` ← `resolve-ips`,
  `public.rdns_city_rules`, `public.rdns_hoiho_rules`, `public.rdns_hoiho_rejected_domains` and `public.rdns_llm_answers` ← `learn-rdns-rules`,
  `public.mlab_hop_names` ← `import-mlab`.
- Schema changes go in `hatchet/schema` (idempotent `IF NOT EXISTS` statements), never by hand. A workflow runs DDL only
  for tables it writes: `ALTER TABLE` takes an ACCESS EXCLUSIVE lock even when the column exists.
- Do not delete rows from `public.asn`; ASNs missing from the source are kept for now.
  `build-asn-data` sets `public.asn.seen_at` for every ASN in the source each run; readers use it to ignore old rows
  (NULL = not yet seen since the column was added).
- `public.asn_geo_pdb` mirrors PeeringDB: `sync-peeringdb` replaces it in one transaction each run, together with
  `public.geo_ix_pdb` (global unicast internet exchange peering LAN prefixes with the exchange's country and city).
  An asn_geo_pdb shrink refuses the whole replace; a geo_ix_pdb shrink or empty result only keeps the old
  geo_ix_pdb rows (`StoreStats.IXKept`) and asn_geo_pdb is still replaced.
- `build-geo-data` reads `public.asn.json` only as its `prefixes` object (`ipdata.PrefixesJSON`, one shared SQL fragment used by the announced-prefix read and the `30-pdb` and `40-hosting` reads; `ipdata.WithJSONFallback` repeats a read with the whole json when Postgres cannot cast one document to jsonb (any data or limit error, SQLSTATE class 22 or 54: invalid JSON, a `\u0000` escape, a number out of range), and a pass writes no layer row until it has read every row). `build-geo-data` only reads these tables and runs DDL only for `public.geo_eval` (`schema.EnsureGeoEval`), never `schema.Ensure`. A missing or empty `public.geo_ix_pdb`
  skips the `50-ix` layer for that run, and missing facility columns or no matching network skip `40-hosting`
  (`Source.SkippedLayers`); a `50-ix` of 1 to 199 usable rows fails, `40-hosting` has no minimum. Exchanges without a
  city are never written to `50-ix`.
  `asn_geo_pdb.fac_count`/`fac_city`/`fac_country` (facilities only, city set only if all are in one city) feed `40-hosting`.
- ip2geo layers have ONE format and ONE name in every stage: a gzipped CSV in the geofeed (RFC 8805) layout, header
  `prefix,country,region,city,source`, named `NN-name.csv.gz` (`10-rir`, `20-ipverse`, `25-bgp`, `30-pdb`, `35-rdns-wide`, `35-speedtest-site`, `36-mlab`, `37-whois-arin`, `37-whois-text`, `38-asn-geofeed`, `39-github-geofeeds`, `40-hosting`,
  `50-ix`, `60-whois`, `65-rdns`, `67-rdns-names`, `68-cloud-regions`, `70-geofeeds`; the number is the order). `build-geo-data` `download` empties its layers dir, each
  source writes its file through the one shared writer (`.tmp` plus rename), and the R2 layers are put in as they are (see the R2 rule below: the last download of each stays in `geo/downloads/` with its ETag, and an unchanged object is copied from there).
  The build passes every `*.csv.gz` in the dir, sorted by name, to `mmdbbuilder geo` (one reader, columns found by header);
  there is no per-layer code and no layer list in the build. Special rules live only in `layerRules` (`geo/pipeline.go`),
  one line per layer name; a rule for an absent file is not passed. A new layer is a new file name, not new code.
  Optional layers (`25-bgp`, `35-rdns-wide`, `35-speedtest-site`, `36-mlab`, `37-whois-arin`, `37-whois-text`, `38-asn-geofeed`, `39-github-geofeeds`, `40-hosting`, `50-ix`, `60-whois`, `65-rdns`, `67-rdns-names`, `68-cloud-regions`) that are absent are listed in
  `Source.SkippedLayers` for reporting (the three rDNS layers are written from `public.rdns_geo_layer` by scope (`wide`, `traced`, `named`), all

  `39-github-geofeeds` is the GitHub geofeed layer: geofeed files (RFC 8805) that operators publish in public GitHub repositories whose name contains `geofeed` and that no whois record links. The task `search-github` of `sync-geofeeds` (no parent, no child, like `probe-domains`; it writes `github.json` in the geofeeds dir and `discover` reads whatever the file holds, so a file found in one run reaches the rows in the next) searches `GET /search/repositories?q=geofeed+in:name` (sorted by update, 100 a page, at most 10 pages, 7 s between requests, 2 s with a token) and uses a repository only when `full_name` is `owner/repo` of `[A-Za-z0-9_.-]`, it is not a fork, private or disabled, its size is above 0, the repository part contains `geofeed`, the default branch is a plain name and the name does not look like a test or a blacklist (the two expressions of the measurement, counted as `skipped_names`). A 401 to a request sent with the token drops it for the rest of the run: that request is repeated without it, the anonymous wait and budget apply from then on, and the output says `token_rejected`. A search answer with `incomplete_results: true` is used but is not complete, so nothing is removed in that run. The temporary files of the feed check live in `<data>/geofeeds/github-check/`, made new at the start of each run and removed at its end. A tree that GitHub cut short (`truncated`) or that is larger than the read limit still counts as listed (the entries that came are used) and is counted in `incomplete`. The file is untrusted: at most 200,000 entries (more: the file is unusable), the file is read with a streaming decoder (a body with more entries is rejected as soon as the limit is passed, not decoded whole; a wrong JSON type anywhere in an entry makes the file unusable). The LABEL of an entry is its `network_border_group` when that is a non-empty string, else its `region` (Local Zones and Wavelength zones carry the PARENT region in `region` and the real place only in the border group: `us-east-1-lim-1` is Lima, so a zone is its own group and never gets the parent's city); an entry needs a label of `[a-z0-9-]{1,48}` after lower-casing and an IPv4 `ip_prefix` between /8 and /32, masked, whose first address is public (`ipdata.PublicV4`), else it is skipped and only counted; fewer than `cloudRegionsMinPrefixes` = 1,000 valid entries: it is not the file, Amazon is left out and the bad copy (with its ETag and stamp) is deleted so the next run fetches again. Where prefixes overlap, the most specific prefix decides the label of an address (the same prefix twice: the first one, but the pseudo label `global` (`GLOBAL` in the file) never wins over a real one); `global` ranges get no row, but a more specific `global` prefix (or a zone) inside a regional prefix still takes its addresses out of that region. Neighbouring prefixes are never merged, so a row is never broader than an entry of the file. Learning: every IPv4 row of `70-geofeeds.csv.gz` that has a city owns its prefix minus the more specific geofeed rows inside it (a repeated prefix: the last row; the code of `25-bgp` is reused, `readBGPFeeds` and `sweepOwned`), and the owned addresses inside a label's ranges are counted per (country, city), the city compared case-insensitively after trimming and written with its most common spelling among the forms that have a lower-case letter (ties: the smaller string; a feed that writes its rows in capitals does not decide the spelling; when every form is in capitals, the most common one). A label QUALIFIES when it has at least `cloudRegionsMinAddrs` = 4,096 such addresses (so a small zone simply gets no row) and its main city (ties: the smaller country, then the smaller normalised name) holds at least `cloudRegionsMinShare` = 80% of them. Every range of a qualifying label gets rows (one per CIDR prefix, disjoint, in address order, region column empty, source `cloud-regions:aws:<label>`) with the main city and ITS country; a row broader than one `10-rir` prefix is dropped by the builder (`-within-first`) and shows in the builder's skipped count for the layer. Rule `-within-first` (it sorts after `67-rdns-names` and before `70-geofeeds`: the operator's own region statement beats router and customer names and whois, and a real geofeed row always beats it; it may change a country, because the region is the operator's own statement of where a range is). The layer file holds the rows of two operators, Amazon (above) and Oracle (below), sorted by prefix; each operator is handled on its own (`cloudOperators`, `geo/cloudregionsdl.go`), so the trouble of one (for Amazon: no qualifying region, no geofeed layer, a failed fetch with no usable copy or an unusable file) only leaves that one out: one log line and its name (`aws`, `oracle`) in `Source.CloudRegionsLeftOut` (`cloud_regions_left_out`). Only when no operator has a row is the layer skipped (`Source.SkippedLayers`, one warning); it NEVER adds to `StaleLayers`, so the `HC_PING_GEO` ping is still sent; cancellation, or a local file error while reading the saved copy or writing the layer in the layers dir, fails; any problem while fetching or saving the region file (also a local one inside the downloader) only skips the layer. `Source` counts `cloud_regions` (labels that got a city; for Oracle the table regions with at least one row) and `cloud_regions_seen` (distinct labels in the files, `global` left out), both summed over the operators whose file could be read. The holdout build takes only the operators that have a row in the layer file of this run (`cloudLayerSources`; the saved copy of an operator `download` left out may be an old one): it recomputes Amazon's rows from the kept feeds and the saved copy of the region file and takes Oracle's rows from its saved copy as they are (they are not learned from geofeed rows; it never fetches); an operator with no saved copy, an unusable one or no row is left out and named in the summary of `prepareHoldout` (`68-cloud-regions.csv.gz without oracle: no saved region file`), and with no row at all the layer is left out. Not in `mmdbStrongSources` of `import-mlab` (unmeasured). Measured on the build of 2026-11-18 by a script, not by the builder: the region file holds 102.1M IPv4 addresses, 79.9M of them already have a geofeed city, 20.6M have none; in every one of the 42 regions the geofeed rows put 97 to 100% of their addresses in one city (only `GLOBAL` has no main city, 12%); the layer gives a place to 16.5M addresses and corrects the country of 14.1M. **Oracle** (2026-11-19; `geo/oracleregions.go`): Oracle's region file `https://docs.oracle.com/en-us/iaas/tools/public_ip_ranges.json` (saved as `geo/downloads/oracle-ip-ranges.json`, the same fetch, cap, `.checked` stamp and 14-day rule) lists `regions[].cidrs[].cidr` per `region` (`eu-frankfurt-1`). Oracle publishes no geofeed, so nothing can be learned: the city of a region comes from the fixed table `oracleRegions` (45 regions, country code and city, the city written as the GeoNames main name so the builder places it), taken from the Region Location column of Oracle's regions documentation and not read from the region code (`uk-cardiff-1` is in Newport). A region that is not in the table gets no row; a new region needs a new line. The file is untrusted and parsed like Amazon's (`parseOracleRegions`: streamed, at most 200,000 entries counted over the whole file, a wrong JSON type anywhere makes it unusable, the `region` key may come before or after `cidrs`; an entry needs a label of `[a-z0-9-]{1,48}` and a masked public IPv4 prefix of /12 to /32 (`oracleRegionsMinBits`: the city of a range comes from the table whatever the range is, so one wrong broad entry would move a large block; the broadest entry of the real file is a /16), else it is counted as bad; an IPv6 range is ignored; fewer than `oracleRegionsMinPrefixes` = 300 valid entries: it is not the file and the copy is deleted). The ranges are made disjoint with the same code (the most specific prefix decides, neighbours are not merged) and every range of a table region gets rows with the source `cloud-regions:oracle:<region>`. An unreadable or unusable file, or one with no table region, only leaves Oracle out. Measured on the build of 2026-11-19: the file holds 4.48M IPv4 addresses in 57 regions, 44 of them in the table (994 rows, 4.33M addresses); 1.86M addresses had no city, 1.25M get another city and 2.97M another country (the registry data labels most of them US); on RIPE Atlas, with the builder on a test build (the rows of the real code on top of that day's database, without the `-within-first` check and above the geofeed rows, which keep 2 of the probes in production), +113 right probes (58.13% -> 58.93%, precision 59.78% -> 60.31%), the table's city right for 136 of the 139 connected probes in those ranges that no geofeed row covers and no probe lost. - **ASN main city fill (`80-asn-main`, a guess)**: not a layer file and not in `layerRules`/`optionalLayers`; it is the one derived fill done inside the builder, because it needs the merged result of all layers. `mmdbbuilder geo -asn-main <asn-prefixes.csv.gz>` (the file `download` saves in `geo/`, gzipped CSV `asn,prefix`) runs after all layers and before the write. IPv4 only (IPv6 rows are ignored; it was measured on IPv4 only). An address belongs to the ASN of the longest announced prefix containing it; a prefix announced by more than one ASN belongs to nobody and still shadows broader prefixes (as in `38-asn-geofeed`). Per group (ASN, country) the addresses that already have a city are counted per city (case-insensitive; when the build has `-geonames`, only cities the GeoNames index places count, the measured definition: cities it cannot place are ignored for the counts but never overwritten; without the index every city counts; with the index a city is the place the index gives it (`placeKey`: its coordinates), so every spelling and name of one place counts together (`São Paulo` and `Sao Paulo`, `Kyiv` and `Kiev`), without it a city is its normalised name; written with the most common spelling, ties by name; the same counting serves `80-asn-main`, `82-asn-likely` and `86-country-main` (`84-asn-near` and `85-holder-city` do not count cities). The holdout build passes no `-geonames`, so there a city is still its name. Since 2026-11-19: before, the two spellings split Brazil's main city (29.4% and 5.5%) under the 30% bar of `86-country-main` and left 17.8M addresses without a city. Checked on that day's build: 18.3M more addresses with a city, 239 countries qualify instead of 238, on RIPE Atlas a net +5 right and -4 wrong probes; a build without `-geonames` is unchanged); the group qualifies when its main city (ties: smallest name) holds at least `asnMainMinShare` = 90% of them and the group has at least `asnMainMinAddrs` = 256 such addresses. Every part of a network of that country that has NO city and belongs to a qualifying group's ASN gets the main city, `city_source` = `80-asn-main`, and coordinates by the same GeoNames rule as layers. It only fills (new insert rule: same `country_code` and no `city_name`); a city or a country is never replaced or changed; the output is deterministic and without the flag byte-identical to a build without it. Measured on RIPE Atlas: right 48% of the time (520 of 1,083 gap probes), fills about 25% of the gap. Printed as `layer 80-asn-main: R rows, P prefixes, 0 skipped` plus `asn-main: G groups qualified of T, A addresses filled`. Guesses are no evidence for our own pipeline: `mmdbbuilder gaps` still lists their /24s (`sample-names` keeps sampling them) and `mmdbbuilder lookup -in/-out` (the MMDB hop votes of `locate`) writes no row for them; the plain `lookup` report shows them, and `eval` scores them like any record (`layer_80_asn_main_*` show the fill alone; `city_pct`, `atlas_city_*` and the holdout city score count the guessed cities like any other, so the first build with the fill moves them; the publish gate checks only country scores and the fill never changes a country). `build-mmdb` passes `-asn-main` when `geo/asn-prefixes.csv.gz` exists (`BuildMMDBOutput.ASNMain` = `on` or `skipped: no ASN prefixes`); a file that cannot be read or has no rows gives `asn_main: skipped: ASN prefixes unreadable` and no flag (never a failed build; the holdout build skips too); `download` deletes that file at the start of its ASN step and writes it again only when it reads `public.asn` (needs the geofeed layer), so a file that is there always belongs to the layers of the same run, never to an older one. The holdout build passes it too, so the fill is recomputed from the kept feeds and held-out feeds never reach it.
- **Fallback guesses (`82-asn-likely`, `84-asn-near`, `86-country-main`; `mmdbbuilder/fallback.go`, flag `mmdbbuilder geo -fallback`)**: three more guesses (and since 2026-11-19 a fourth, `88-asn-far`, described at the end of this rule) for the IPv4 addresses that still have a country and no city after `80-asn-main`; like it they are not layer files and not in `layerRules`/`optionalLayers`. The guesses are one ladder (`fillGuesses`): each cityless part gets the FIRST guess that applies, in the order of the numbers. `82-asn-likely`: the main city of the (ASN, country) group when it holds at least `asnLikelyMinShare` = 70% of the group's addresses with a city, no minimum number of addresses. `84-asn-near`: the city of the nearest piece of the same group that has a city (a piece = the part of a tree leaf inside the ASN's segment), decided per /24-aligned chunk of the cityless part by the chunk's middle address: the nearer of the last piece starting before it and the first piece after it wins (equal distance: the bigger piece, then the earlier one), and it counts only when its nearest edge is in the same /20 as that address; a chunk with no such piece falls to the next guess. `86-country-main`: the country's main city over ALL addresses with a city (with or without an ASN, ties: smallest name) when it holds at least `countryMainMinShare` = 30% of them; it also fills addresses of no ASN, and a country below 30% is left without a guess (there the main city was right for 14 of 273 probes). All evidence (group sums, pieces, country sums) comes from ONE snapshot of the tree taken after all layers and before the first guess is written, and every cityless part is given to its guess before the first insert, so a guess is never evidence for another guess and the printed counts are real fills. The same rules as `80-asn-main` hold: with `-geonames` only cities the index places count, the insert rule only fills (same `country_code`, no `city_name`), IPv4 only, coordinates by the GeoNames rule, deterministic. `-fallback` without `-asn-main` runs only `86-country-main`; without `-fallback` the output is byte-identical to before (checked against the old binary on a real build: only the build epoch differs). All four sources (and `85-holder-city`, see the next rule, and `88-asn-far`, see the end of this rule) are in `guessSources` (`isGuessSource`) and in `noSampleSources`: `mmdbbuilder gaps` still lists their /24s and `lookup -in/-out` writes no row for them; `eval` scores them like any record (`layer_82_asn_likely_*`, `layer_84_asn_near_*`, `layer_86_country_main_*`). Each prints `layer <name>: R rows, P prefixes, 0 skipped` (so it is in `prefixes` of the `build-mmdb` output) and a note (`asn-likely: G groups qualified of T, A addresses filled`, `asn-near: A addresses filled`, `country-main: C countries qualified of T, A addresses filled`). `build-mmdb` and the holdout build ALWAYS pass `-fallback` (`fallbackFlag`, `BuildMMDBOutput.Fallback` = `on`), also without the ASN prefixes and on the retry without GeoNames. Checked on the build of 2026-11-16 with RIPE Atlas (within 50 km): `82-asn-likely` right for 161 of 367 probes (44%), `84-asn-near` 134 of 396 (34%), `86-country-main` 587 of 1,331 (44%); together +882 right and +1,212 wrong probes, right city of all probes 48.1% -> 54.3%, precision of all answers 59.0% -> 56.4%, 906M addresses filled (239 of 243 countries qualify), MMDB about 2.5% bigger, same memory. **`88-asn-far` (2026-11-19)**: a sixth guess, the last rung, also under `-fallback` with the ASN prefixes (no flag of its own). It is for the /24 chunks of a cityless part of an announced network that `84-asn-near` gave nothing AND whose country has no main city (on the build of 2026-11-19 the United States, where no city reaches the 30% bar of `86-country-main`, with 115.3M of the filled addresses, and Algeria, Kazakhstan and Bosnia with 0.4M together; such a chunk stayed without a city before): the city of the nearest piece of the same (ASN, country) group by the rule of `84-asn-near` (`nearPiece`), when that piece's nearest edge is in the same /16 as the chunk's middle address (`asnFarSameBlock` = 16; rung 84 uses the same /20); else the chunk stays without a city. In a country that has a main city nothing changes: the chunk gets `86-country-main` as before, never `88-asn-far`. A part with no ASN, or in a prefix of several ASNs, or of a group with no piece, is unchanged too. The rules of the other guesses hold (one snapshot, every chunk given to its rung before the first insert, only fills, IPv4 only, deterministic); it prints `layer 88-asn-far: R rows, P prefixes, 0 skipped` after `86-country-main` and the note `asn-far: A addresses filled`; `eval` scores it as `layer_88_asn_far_*`. It is a weak guess, built to cover address space and kept under its own source name so that a user of the file can leave it out. Measured on a test build of 2026-11-19 (that day's database with a stand-in holder file): 115,739,754 addresses filled and no other address changed (3.1 points; addresses with a city about 87.2% -> about 90.4%), right for 10 of the 49 RIPE Atlas probes it answers (20%: +10 right and +39 wrong probes, 17 of the wrong in one network, AS16552; precision of all answers about 60.28% -> 60.14%). Wider limits were measured the same day and not used: same /12 221.6M addresses, 11 of 54 probes right; no limit 391.8M addresses, 17 of 76 (22%). A second check (the city of every US probe's own piece hidden, the guess made from the nearest other piece of its network, no limit): beyond a /20 right for 14% to 34% of the probes, depending on how much is hidden.
- **Holder city guess (`85-holder-city`; `mmdbbuilder/holders.go`, flag `mmdbbuilder geo -holders <holder-cities.csv.gz>`)**: a fifth guess, for IPv4 address space that NO network announces: a part with a country and no city that lies inside an address block whose holder (the registrant of the ARIN record) has a known city gets that city, before `86-country-main`. Like the other guesses it is not a layer file and not in `layerRules`/`optionalLayers`. `-holders` needs `-asn-main` (the announced prefixes say what is unannounced; without it the builder exits with `-holders needs -asn-main`) and does not need `-fallback`. Announced space is the union of ALL IPv4 prefixes of the asn-prefixes file, also a prefix announced by more than one ASN (`readASNData`: such a prefix has no ASN segment, but it is announced), so a part with an ASN, or in a prefix of several ASNs, never gets the holder city: the guesses 80 to 84 and their fall to 86 are unchanged. The file is a gzipped CSV in the layer layout (`prefix,country,region,city,source`, read with `readLayer`) and untrusted: a row is used when its prefix parses, is IPv4 and no broader than a /8, its country is two letters and its city passes `cleanCity`; every other row is counted in the skipped number of the guess's layer line. The most specific block decides an address (the same prefix twice: the last row), and a block fills only where its country is the country of the address. The rules of the other guesses hold: evidence only from the one snapshot (a holder fill is never evidence for `86-country-main`), every part is given to its guess before the first insert, it only fills (`whereCountryNoCity`), IPv4 only, coordinates by the GeoNames rule, deterministic; the holder city is not checked against the builder's GeoNames index (the exporter placed it). Without `-holders` the output is byte-identical to before. The source is in `guessSources` (`isGuessSource`, `noSampleSources`): `mmdbbuilder gaps` still lists its /24s (the walk of `sync-arin-whois` and `sample-names` keep working there) and `lookup -in/-out` writes no row for it; `eval` scores it like any record (`layer_85_holder_city_*`), and `city_pct` counts its cities. Checked on the build of 2026-11-19 with the records of 3,589 lookups (2,941 blocks of US records; a stand-in file made by a script, not by `export`): 182.2M addresses filled, none in an announced network, none with a city or another country before, no other address changed, and without `-holders` the file differs from the old binary's only in the build epoch. Blocks of every holder class are in the file, the military ones too.

- `learn-rdns-rules` has a third task, `import-hoiho` (the order is `learn` -> `import-hoiho` -> `propose-codes`, because the three tasks share the dictionary cache files (`cities1000.zip`, `admin1CodesASCII.txt` and the Hoiho file are downloaded through the same `.tmp` name by `download.File`), so they must not run at the same time; a failing `learn` therefore also stops `import-hoiho` and `propose-codes`; same `rdns-rules` limit; execution timeout 30 minutes; CLI `run-rdns-rules -hoiho`, which cannot be combined with `-reject` or `-codes`; skipped with `reject_domains`; `ImportHoiho` in `rdnsrules/hoiho.go`, the pure conversion in `rdnsrules/hoiho_convert.go`, table DDL `schema.EnsureRDNSHoihoRules`). It imports the router-name rules of CAIDA's Hoiho, published with the Internet Topology Data Kit (ITDK 2024-08): regular expressions that find the location code in a router's DNS name, per DNS suffix. Source: the constant `hoihoURL` (`.../itdk/2024-08/midar-iff.geo-re.jsonl`, about 2 MB, 823 lines), fetched into the learner's dictionary cache (`rdnsrules/dictionaries/hoiho-geo-re.jsonl`) with `fetchSource` (30-day check, conditional download, `.checked` stamp written only after the import accepted the file). `download.File` has no size limit, so the client is wrapped (`capClient`): a response that announces more than 32 MB fails at once and a body that grows past it fails while reading, so the temporary file never passes the limit. The file is untrusted. A file with fewer than `hoihoMinRecords` = 300 records parsed is not the file (`skipped: too few records`). Keys are capped because the file is untrusted and one regex can emit hints times splits times countries keys: a regex that would get more than `hoihoMaxRowKeys` = 50,000 keys is skipped (`regex_too_many_keys`; the key map stops growing as soon as the limit is passed; the real file's largest row has 4,465), and when the running total of the whole conversion passes `hoihoMaxKeys` = 500,000 (the real file gives 28,192) the conversion stops and returns no rows (`skipped: too many keys`, the table stays). Conversion (pure, deterministic: same file and GeoNames give the same rows, sorted by domain and seq): a regex is skipped (reason counted) when it does not compile as `(?i)` plus the pattern in Go, its group count differs from the plan, the plan has an unknown type, no location type, two different location types, a location type twice (except `clli,clli` on adjacent captures) or more than one `cc` or `st`. For every hint of the plan's location type the city is found (below) and the key is built in capture order: the lower-case hint code, the lower-case country code of the place for `cc` (for GB also the same key with `uk`) and the lower-case `location.st` for `st` (the top-level `st` for a facility hint; a hint with no state is skipped for that regex and counted once as `hint_no_state`); for `clli,clli` one key for every split of the code in two non-empty parts. Two hints with the same key: the larger `tp` wins, then the smaller city name, so a key never appears twice. A regex with no key gives no row. City of a hint with a location: among the GeoNames places named `place` in the country (`geoIndex.byName`), those within `hoihoNameRadiusKm` = 50 km of the coordinates, the first by more people, then the smaller name, then the smaller id; else the first of the places of the country within `hoihoNearbyRadiusKm` = 30 km by the same order; else none (bad coordinates or an unknown country too). The city stored is the place's GeoNames name and country. City of a `clli` hint (no location; the CLLI guess): the code must be six letters, four that abbreviate a place name and a two-letter region. The codes `nycm`, `nycq`, `nyck`, `nycx` and `nycr` with region `ny` are New York City. The region is a US state or DC (country US, admin1 the code) or a Canadian province (AB BC MB NB NF NL NS NT NU ON PE PQ QC SK YT: country CA, admin1 01 AB, 02 BC, 03 MB, 04 NB, 05 NL and NF, 07 NS, 08 ON, 09 PE, 10 QC and PQ, 11 SK, 12 YT, 13 NT, 14 NU). Candidates are the GeoNames places of that country and admin1 whose ASCII name, lower-cased with everything but a-z removed, starts with the first letter of the abbreviation and holds its four letters in order; the most populous wins (ties: smaller name, then smaller id). A plan without `cc` is used only when the region is a state or province (the `st` part is the region code); a plan with `cc` also emits `us` or `ca` for the region's country and, for every other country, a key when a place of at least `hoihoBigCityPop` = 100,000 people abbreviates the four letters (the last two letters are then CLLI's own country code, which the captured country decides; GB also as `uk`). a base that is there but cannot be opened, or a read that fails on the disk, is an error and the file is left alone, in `Progress` and in `Compact` (not damage, not a lost base: nothing is fetched or written over it); a base whose CONTENT is bad is renamed to `records.damaged` in one step: in `Compact` when it cannot be read to its end (the task fails with `errDamaged`), in `Progress` when its first line is not a position line (a WARNING, then R2 decides: restore, `startBase` or `skipped`); `records.damaged` is removed after a restore from R2 and KEPT when the walk starts again (it is the last copy of that data). Before a restore download, part files left by a killed download are removed. A run that stops on `failing` or `rate limited` logs a WARNING with the position (the same line run after run means the walk is not moving). `upload` copies the base to `RecordsKey` when `backup.json` is missing or 24 hours old (`force_upload` skips the wait), ALWAYS refuses it (`backup: refused`, a WARNING with both counts; also with `force_upload`; delete `backup.json` to accept a smaller file on purpose) when it has less than half the records of `backup.json`, and never sends a base it cannot read; `RecordsKey` is this workflow's own backup, no other workflow reads it. **`holders.csv`** (`arin/holders.go`, same directory, mode and `.tmp` rules; no gzip, no position line): CSV with the header `net_start,net_end,country,state,city,class,looked_up` (`class` is `edu`, `gov`, `mil` or `other`, never a name; country, state and city may be empty in a replacing row, see below). `lookup` appends, per stored batch and one row per range, (a) every `wide` answer whose range is at most `maxHolderBlock` = 16,777,216 addresses (a /8) with a usable country, state and city, whatever its class, (b) every `found` answer with a usable city whose class is `edu` or `gov`, and (c) every `found` answer whose range is the range of an edu or gov row that is the newest row of that range in the file (loaded at the start of `lookup`, kept up to date during the run), with the class and city it has now, also class `other` or `mil` and also with no usable city: the newest row of a range wins in the compaction and only edu and gov rows with a city reach the layer, so such a row switches the old one off. A `found` record of class `other` or `mil` of an unknown range is only in the main records, and a wide answer without a usable city or wider than a /8 is dropped. The rows are appended and fsynced BEFORE the journal and the position are written (so a crash only repeats rows, never loses them behind the position; a half row is cut off by the next append like in the journal and a row that does not parse is skipped); the batch counts go to `holders_stored`, `holders_edu`, `holders_gov`, `holders_mil`, `holders_other` (`wide` keeps its meaning). `export` compacts it after the main `Compact` (one row per range, the newest `looked_up`, rows older than 300 days dropped, `holders_pruned`, sorted by start then end, through a `.tmp` file); a missing file is an empty set, a file that cannot be read or written is skipped (`holders_unreadable`, a WARNING) and the layer is made as without holders. Backup: `upload` copies the file gzipped (no time in the header, so the same rows give the same bytes) to the fixed key `internal/arin/holders.csv.gz` (`HoldersKey`) at most once every 24 hours (`holders-backup.json` = `{"uploaded_at","records"}`, `force_upload` skips the wait). Like the records backup it is REFUSED when the file has less than half the rows the state file recorded (`holders_backup: refused`, a WARNING with both counts, also with `force_upload`, the state file untouched; delete `holders-backup.json` to accept a smaller file on purpose); the row count is also written at each successful upload and at a successful restore, so the refusal holds after a wipe. Any other problem is only the output `holders_backup` (`uploaded`, `unchanged`, `recent`, `refused`, `failed`) and never fails the task. `lookup` restores the file when `holders.csv` is missing and R2 has the object (output `holders_restore`: `restored` or `failed`; part files of a killed download are removed first; no R2 setting: nothing; the main records restore is not touched). When the restore answers `failed` (R2 has, or may have, a copy that could not be fetched or read), that run appends NOTHING to `holders.csv` and does not create it (the rows are dropped for holders only and counted in `holders_skipped`, one WARNING), everything else of the run goes on, and the next run tries the restore again: a new file would hide the copy. The records backup and the holders backup are two separate daily copies, so after a wipe the restored walk position can be newer than the restored holders copy; the rows in between are found again only in the next cycle. Layer rule: the compacted holder rows of class `edu` or `gov` with a usable country, state and city and at most `maxStoredBlock` = 65,536 addresses (a /16) go through exactly the placing rule of the main records (GeoNames place of that name in the record's own state, not ambiguous) and the same row writer, source `whois-city:arin`; for the same prefix the smaller record wins, and for the same range (a holder row and a main record) the one looked up later wins, then the main record first; `export` reports `holder_records`, `holder_candidates` (edu or gov, at most a /16, with a city) and `holder_rows` (layer rows that came from them); the drop counters are shared with the main records; `no rows` means no row from either input.

- `sync-bgp` (cron `40 3 * * *` UTC, own `bgp` limit, tasks `download` -> `extract` -> `upload`; CLI `run-bgp [-skip-upload | -force-upload] [-mrt file]`, `-mrt` reads a local dump and uploads nothing; input `skip_upload`, `force_upload`) reads no database and no other workflow's files. `download` fetches the public RIPE RIS dump `https://data.ris.ripe.net/rrc00/latest-bview.gz` (about 430 MB) into `/var/lib/openipdata/bgp/` with the shared `hatchet/download` (conditional, one file only, no new request within 6 hours of the last check, plain client with timeouts, 2 GB cap). A newly downloaded dump is read through once (`checkGzip`, the gzip checksum covers every byte): a damaged one is deleted with its ETag and `.checked` stamp (`removeDump`) and fetched a second time (`fetchTries` = 2); two damaged files fail the task with no dump left, so the age gate never keeps a bad file. `extract` streams the MRT file in two passes (TABLE_DUMP_V2: PEER_INDEX_TABLE and RIB_IPV4_UNICAST, other types and subtypes ignored; attributes COMMUNITIES and LARGE_COMMUNITY; every length checked, damaged input is `bgp.ErrDamaged`, never a panic; a broken gzip stream (bad header or checksum, corrupt deflate data, a file that ends early) is `ErrDamaged` too (`asDamaged`), and when the dump is Download's own, `extract` deletes it with its ETag and stamp and fails without retries (a retry of `extract` alone would read the same file; a file named with `-mrt` is never deleted): pass 1 counts in how many prefixes each value occurs, pass 2 writes `bgp-communities.csv.gz` (`.tmp` plus rename), header `prefix,communities`, one row for EVERY IPv4 prefix of /8 to /24 (also one with no value left), values space-separated, `a:b` standard and `a:b:c` large. A value carried by more than 5% of all prefixes or by fewer than 3 is dropped. A dump with fewer than 500,000 prefixes fails (`ErrTooFewPrefixes`, not retried). `upload` puts the file at the fixed key `internal/bgp/communities.csv.gz` exactly like the sync-geofeeds layers (sha256 in the user metadata, an identical object is not sent again and its `LastModified` is renewed, `force_upload` always sends), then pings `HC_PING_BGP` (optional; never logged; a failed ping only logs). Task outputs are counts. Measured on a real dump: 1.16M prefixes, 27.7 MB, 30 s, 55 MB peak memory.

  The holdout leaves out a frozen sample of feeds, read from `public.geofeed_urls` (`id % 10 = 0`, `first_seen_at` before the
  freeze date in `hatchet/geo/holdout.go`); a failed read is an evaluation error, never a different sample. Moving the date moves the score once. `eval` also breaks the holdout city score down by the `city_source` of the holdout database's record (the way the Atlas per-layer keys read it, `sourceKey`): `layer_<src>_holdout_city_answered` and `layer_<src>_holdout_city_right` (written when `answered` is above 0) and `holdout_city_unanswered` (truth rows with a city whose record has no city, or no record); the answered counts plus unanswered add up to the rows with a city, and the right counts to the rows `holdout_city_pct` counts as right, so a step in `holdout_city_pct` shows which layer gained or lost the held-out prefixes.
